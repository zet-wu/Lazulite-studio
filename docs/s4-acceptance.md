# S4 行级制作闭环验收

日期：2026-09-12。S4 功能闭环验收通过；性能目标与模型质量验证边界如下。

## 实现范围

- 真实项目从富 TTML 建立工作副本，所有歌词变更经过领域命令；保存串行提交，以独立编辑序号和随机幂等键处理在途修改与重试。
- TTML/LRC/纯文本先导入候选。搜索、取词、转写和行对齐运行于持久任务队列，结果绑定输入项目、资产、修订及引擎身份，人工查看差异后作为单次事务应用。未保存修改或旧输入阻止应用。
- 基础歌手增删、改名和行分配；已有 Ruby、结构化文本与不支持的时间表达式维持保真及只读边界。
- 复核状态具有独立版本。歌词保存与受影响行复核失效在同一事务完成；无关行保留确认。
- 本地检查点恢复、双页面冲突处理、草稿下载与服务器重载；正式 TTML 经既有 codec 校验后导出。
- 桌面三栏、窄屏单面板切换、键盘选行，沿用底部媒体播放区。

## 已执行验证

- 服务端完整测试：17 项通过，覆盖文档 CAS、幂等、导入不落稿、复核原子失效、任务持久化、重启与排队取消，以及正文投影。
- 前端单元/集成测试：36 项通过，包含保存期间继续编辑的最新检查点、响应失败重试、旧修订恢复冲突、歌手保真与候选映射。
- Chromium 浏览器回归：5 项通过，保留本地编辑器、恢复、工作区导航、窄屏、任务与导出检查。
- TypeScript 与生产构建通过。

主 Agent 另外使用真实 Studio HTTP 服务、真实 Lazulite 调度、合成音频及可注入的合成歌词来源/转写后端，在浏览器验证：

1. 上传音频 → 创建项目 → 搜索 → 取词 → 查看差异 → 人工应用 → 自动保存。
2. 行复核确认 → 行对齐候选应用 → 保存 → 受影响行需要重新确认。
3. 转写候选应用 → 保存 → 刷新重开。
4. 保存请求不可用时编辑 → 刷新 → 恢复本地检查点 → 恢复保存。
5. 添加四名歌手 → 行分配 → 保存 → 重开保留 → 下载正式 TTML。
6. 两个页面修改相同修订时，后提交页面显示冲突且可以下载本地稿。
7. 1440×900 与 390×844 布局检查，窄屏无横向溢出。

上述闭环未发现浏览器脚本错误。合成后端仅验证引擎接口、秒/微秒转换和应用流程，不代表真实模型识别质量或在线歌词来源可用性；未安装模型权重，也未修改并列 Lazulite 引擎源码。

## 性能与边界

2,000 行合成 TTML，Chromium 140.0.7339.16，1440×900，Linux x86_64 / AMD EPYC 7502。首次开发构建测量：候选应用至 2,000 行 DOM 可见约 964ms，单次编辑动作约 455ms。此数值包含 Playwright 调度，不等同于纯渲染时间或 p95；不据此宣称达到架构 50ms / 60fps 目标。虚拟行表复测仅渲染 26 行，候选显示约 289ms，编辑动作约 142ms；深链接到第 2,000 行、手动滚动和键盘聚焦另行通过。性能目标仍需后续用生产构建进行 p95/帧率专项测量。本轮使用 15 秒合成音频与 2,000 行，不是完整的 10 分钟/20,000 细粒度单元基准。

模型配置见 [服务运行说明](../server/README.md)。本阶段未执行 GPU 模型质量基准、细粒度强制对齐、Ruby 编辑、stpp 发布或部署。
